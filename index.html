Executive Summary

The Trio DIY automated insulin delivery app utilizes GitHub Actions to compile native iOS binaries on cloud-hosted macOS virtual machines (such as macos-14, macos-15, and macos-26). Because thousands of users fork the upstream repository to build and sign personalized TestFlight installations, this ecosystem serves as a large-scale natural experiment on the availability, queue contention, and diurnal failure patterns of GitHub's macOS hosted runner fleet.

This investigation performed an exhaustive 100% census of all 2,437 public forks of nightscout/Trio, analyzing 41,410 individual executions. All 14,269 non-successful runs were inspected at the individual job, step, runner ID, and check-run annotation level to distinguish between normal Fastlane/signing failures and true macOS runner capacity exhaustion.

Diurnal Time-of-Day Analysis (24-Hour UTC Curve)

A rigorous breakdown of manual build dispatches (workflow_dispatch) demonstrates a pronounced diurnal congestion curve driven by global developer working hours:

Acute Peak Window: 14:00 – 17:00 UTC (10:00 AM – 1:00 PM US Eastern)
During this 3-hour window, the manual build failure rate due to macOS runner starvation peaks at 5.2% – 6.2%. This represents the global overlap between North American morning working hours and European afternoon working hours, when corporate and open-source CI pipelines saturate GitHub's shared macOS pools.
Optimal Safe Window: 22:00 – 11:00 UTC (Late US Evening / Morning Europe)
During late North American evening through European morning hours, runner starvation drops to near zero (< 1%). At 03:00 and 23:00 UTC, the empirical starvation rate across thousands of runs is only 0.3%.

Historical Timeline & Infrastructure Shifts (2024–2026)

Tracking runner starvations across the 2-year timeline reveals two major inflection points in GitHub Actions macOS infrastructure:

Incident 1: October 1, 2025 Outage
On Wednesday, October 1, 2025, a concentrated GitHub Actions infrastructure outage caused 139 scheduled cron builds to simultaneously fail at 08:00 UTC with the annotation: "The job was not acquired by Runner of type hosted even after multiple attempts".
Incident 2: October 2026 Migration to Apple Silicon (macos-26)
In October 2026, Trio migrated its default runner from x86 to Apple Silicon macos-26 (Xcode 26). The smaller M-series runner pool caused a sharp resurgence in queue timeouts, producing 176 runner-lack failures (44.5% of all runner failures in project history) and frequent capacity warnings.

Day-of-Week Dynamics: The Sunday Inoculation

Despite Sunday representing 73.5% of all project runs (30,448 executions), it exhibits the lowest failure rate across the entire week (0.25% overall, 0.84% manual).

Architectural Insight: Upstream Linux Gating
Trio’s build action runs preliminary update checks (check_status) on ubuntu-latest. If there are no new commits upstream and it is not the designated monthly build day, the job cleanly terminates itself via cancel_when_no_build on Linux. Consequently, thousands of Sunday runs never enter the expensive macOS runner queue, insulating users from runner pool depletion.

Methodology & Privacy Protocol

Data Extraction Pipeline: Data was acquired using the GitHub REST API across all 25 pages of public forks of nightscout/Trio. For each repository, the build_trio.yml workflow endpoint was queried, capturing full run metadata. All failed or cancelled runs were subsequently evaluated via the Jobs API and Check-Runs API.

Diagnostic Criteria for Runner Lack: A workflow run was classified as a runner lack failure if and only if:

  • A macOS target job (macos-26, macos-15, macos-14) finished with status cancelled, failure, or timed_out; AND
  • runner_id == 0 or runner_name == "" (indicating no VM host was ever bound); OR
  • Check-run annotations explicitly contained "The job was not acquired by Runner of type hosted even after multiple attempts" or "Due to capacity constraints, jobs targeting macOS arm64 runners may experience longer queue times."

PII Anonymization Protocol: In strict compliance with privacy best practices, all personal identifiable information has been redacted:

  • Zero personal GitHub usernames, email addresses, or repository URLs are included in exported datasets.
  • All records are aggregated into temporal bins (hourly, daily, monthly) and categorical failure distributions.
  • Raw reproduction data files are provided strictly as anonymized aggregated tables in the data/ folder.

Practical Recommendations for Trio Fork Builders

1. Schedule Manual Builds for Night / Early Morning UTC
If building manually via the GitHub Actions browser UI, trigger your build between 22:00 UTC and 11:00 UTC (late US evening or European morning) for a ~99% runner allocation rate.
2. Avoid the 14:00 – 17:00 UTC Peak
Avoid triggering manual builds between 10:00 AM and 1:00 PM US Eastern. Approximately 1 in 16 manual builds initiated during this window encounters long queue stalls or runner allocation drops.
3. Preserve Upstream Linux Validation
Do not modify the workflow to eliminate the ubuntu-latest pre-check. Running pre-flight checks on Linux prevents forks from congesting macOS pools during weekly automated checks.
